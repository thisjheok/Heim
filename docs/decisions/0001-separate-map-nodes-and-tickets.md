# 0001. 지도 노드와 개발 티켓 분리
- 날짜: 2026-10-26
- 상태: 채택

## 맥락
노드가 지도 구성품이면서 개발 작업 단위(next node, 구현 상태)까지 맡았다.
- 작업 단위 spec이 (project, map_revision, node)에 묶여 맵이 바뀔 때마다 spec 생성 LLM → next 추천 LLM이 연쇄 재실행됐다.
- 노드1 개발 후 노드2 작업 중 노드1을 고치는 일이 흔한데, "완료 노드는 next 제외" 규칙과 맞지 않았다.
- next를 LLM으로 계산하는 것은 복잡도 대비 이득이 작았다.

## 결정
- **지도(노드)** = 사용자와 AI가 공유하는 프로젝트 구조 어휘. 진행 상태를 갖지 않는다. `data.status`는 사용자 메모일 뿐 로직에 쓰지 않는다.
- **티켓** = 사용자가 dev를 지시하는 단위이자 Codex 세션 단위. 맵 revision과 무관하게 존재한다.
  상태 `todo` / `in_progress` / `done`, 순서(position), 생성 주체(agent/user), 연관 노드 N개(`ticket_nodes`).
- **기능(feature)** = 티켓을 묶는 한 단계 상위 엔티티. 완료 여부는 하위 티켓이 모두 done인지로 파생.
- **next** = LLM 없이 결정적으로: 기능 순서 → 티켓 순서상 첫 todo 티켓. 티켓 간 의존성은 1차 범위에서 제외.
- LLM은 사용자가 요청할 때만 기능을 티켓 목록으로 분해(`ticket_plan`)한다.
- 지도와 티켓의 연결 고리:
  1. 티켓 개발 시 연관 노드의 설명·관계를 프롬프트에 주입한다.
  2. 노드에서 연관 티켓 이력·현황을 파생해 보여준다(지도 위 오버레이).
  3. 티켓 완료 후 구조가 바뀌었으면 기존 초안→승인 흐름으로 지도 변경을 제안한다.
- Agent 계약: `unit_plan`→`ticket_plan`, `unitId`→`ticketId`, `next_development_node` 제거 → `contractVersion: 2`.
- 기존 `development_*` 테이블 데이터는 이전하지 않는다(마이그레이션 체계 없음, 출시 전).

## 기각한 대안
- 지도 제거, 티켓만 유지 — 사용자의 구조 이해와 AI 맥락 공유라는 Heim의 핵심 의도를 잃는다.
- 노드 구현 상태 유지 + next 제외 규칙 보완 — 노드 간 상호 수정이라는 현실과 근본적으로 충돌.
- 부모-자식 티켓(재귀) — 한 단계 기능 엔티티로 충분하고 더 단순.
- LLM 기반 next 추천 유지 — 재계산 비용·복잡도가 크다.

## 결과
- `next_development_recommendations`, `eligible_development_nodes`, 노드·revision 단위 spec 제거.
- 지도가 실제로 쓰이도록 1·3번 연결 고리를 반드시 구현해야 한다(안 쓰이면 지도가 현실과 어긋난다).
- 티켓 의존성(`depends_on`)은 후속 과제.
